Stanford CS336 (1) Assignment 1 — Byte Pair Encoding

2026年5月13日

背景

Stanford CS336 是 Stanford 开设的一门关于大语言模型（LLM）的课程，涵盖了从预训练到后训练的完整 pipeline。这是该课程的第一个 assignment，目标是手动实现一个健壮且高效的 Byte Pair Encoding (BPE) 分词器。在这篇文章中，我将梳理 BPE 的底层逻辑以及我在实现过程中踩到的工程坑。

前置知识：底层数据表示

1. Unicode 标准与 UTF-8 编码

一切文本处理的起点都是字符编码。Unicode 本质上是一个巨大的“映射字典”，它给世界上几乎所有现代字符分配了一个唯一的数字（比如 1~15w 的范围）。

而 UTF-8 则是将这些 Unicode 字符编码为计算机可读的字节流的具体方式。这是一种变长编码，有的字符用 1 个字节，有的需要 2 到 4 个字节：

  • 'h'：对应 Unicode 104，UTF-8 编码为单字节：01101000 (0x68)。
  • 'こ'：对应 Unicode 12371，UTF-8 编码为 3 个字节：0xE3 0x81 0x93。
  • '你'.encode("utf-8")：结果为 b'\xe4\xbd\xa0'。
踩坑点：在作业的 decode_utf8_bytes_to_str_wrong 函数中一定会失败。因为如果你试图将 UTF-8 字节流中的每一个字节单独拿去 decode，遇到像 \xe3 这样的字节就会报错。它只是一个多字节字符（如日文或中文）的起始标识，本身并不代表一个完整的字符。

2. 为什么不用纯 Byte-level Tokenization？

既然所有文本都能转成字节，为什么不直接把字节丢给模型训练？如果基于 UTF-8 的字节序列直接训练，那么原本 10 个英文单词，转换为字节后可能变成 30 个字节。这会导致序列长度（Sequence Length）暴增，极大地影响 Transformer 模型的训练和推理效率（Attention 机制的计算复杂度是序列长度的平方）。因此，我们需要引入子词分词。

Byte Pair Encoding (BPE) 算法核心

1. BPE 的诞生与思路

2016 年，Sennrich 将数据压缩领域的 BPE 算法引入 NLP 领域。核心思想是：如果 t-h-e 这三个字节经常相邻出现，就把它们合并为一个单一的 Token：the。通过这种自底向上不断合并高频组合的方式，能在“防止序列过长”和“控制词表大小”之间找到完美平衡。

2. Pre-Tokenization（预分词）

如果不加限制地直接在整个语料上做 BPE 合并，很可能会出现 "dog!" 和 "dog." 这样语义相同却占据不同 Token ID 的情况。为了避免跨单词或跨标点符号的非法合并，在正式 BPE 之前，需要先进行一次粗粒度的分词，将文本切分为独立的词元（chunks）。

3. 合并规则与“字典序”

BPE 的核心流程就是：将词元转化为 UTF-8 编码 -> 统计相邻 Pair 频次 -> 选出最高频合并 -> 更新词表。这里有一个关键的边界规则：当有多个 Pair 频次一致时，按字典序（Lexicographical order）更大的优先合并。

所谓字典序，就是按字符在 ASCII 码表中的大小逐位比较。比如数字 < 大写字母 < 小写字母。在 Python 中，直接对比 bytes 类型（例如 b'a' > b'b'）原生就是严格的字典序比较，这在维护优先队列（大顶堆）时非常方便。

代码实现与架构优化

手动实现一个处理千万级语料的 BPE 分词器，如果不做架构优化，跑几天都跑不完。以下是我在实现过程中的核心模块拆解。

模块一：大顶堆与字典序 Tie-breaker

为了在 $O(\log N)$ 时间内找到最高频的 Byte Pair，我们需要维护一个大顶堆。由于 Python 内置的 heapq 是小顶堆，且我们需要在频次相同时按“字典序降序”破局，因此需要重写 __lt__ 魔术方法。

import heapq
from typing import Tuple, Optional, List

class _HeapItem:
    """
    堆元素包装器，实现以下排序逻辑：
    1. count降序 (通过存负数实现小顶堆模拟大顶堆)
    2. pair字典序降序
    """
    __slots__ = ['neg_count', 'pair', 'count']

    def __init__(self, pair: Tuple[bytes, bytes], count: int):
        self.pair = pair
        self.count = count
        self.neg_count = -count
    
    def __lt__(self, other: '_HeapItem') -> bool:
        if self.neg_count != other.neg_count:
            return self.neg_count < other.neg_count
        # 当频次相同时，字典序更大的排在前面（因为是模拟大顶堆）
        return self.pair > other.pair

class BytePairMaxHeap:
    __slots__ = ['_heap']

    def __init__(self):
        self._heap: List[_HeapItem] = []

    def push(self, pair: Tuple[bytes, bytes], count: int) -> None:
        heapq.heappush(self._heap, _HeapItem(pair, count))

    def pop_most_frequent(self) -> Optional[Tuple[Tuple[bytes, bytes], int]]:
        if not self._heap:
            return None
        item = heapq.heappop(self._heap)
        return item.pair, item.count

class BPEVocab(BytePairMaxHeap):
    def __init__(self):
        super().__init__()
        # 外层构造dict类型，用于懒惰删除（Lazy Deletion）验证最新频次
        self.valid_counts = {}
    
    def push(self, pair, count):
        self.valid_counts[pair] = count
        super().push(pair, count)
    
    def pop_most_frequent_valid(self):
        while self._heap:
            pair, count = super().pop_most_frequent()
            if self.valid_counts.get(pair, 0) == count:
                return pair, count
        return None

    def add_count(self, pair, count):
        """基于某个pair增加或减少count"""
        old_count = self.valid_counts.get(pair, 0)
        new_count = old_count + count
        self.push(pair, new_count)

模块二：安全的文件切块与预分词

处理 GB 级别的大文件时，不能一次性读入内存。我们需要将文件切分（Chunking）。这里的坑在于：不能暴力切分字节，否则会把形如 <|endoftext|> 的特殊标记拦腰截断。我们需要一个安全的寻址函数。

from typing import BinaryIO
import os

def find_chunk_boundaries(
    file: BinaryIO,
    desired_num_chunks: int,
    split_special_token: bytes,
) -> list[int]:
    """
    将文件安全地切分成可以独立统计的块，确保不在 Special Token 内部断开。
    """
    assert isinstance(split_special_token, bytes)
    file.seek(0, os.SEEK_END)
    file_size = file.tell()
    file.seek(0)

    chunk_size = file_size // desired_num_chunks
    chunk_boundaries = [i * chunk_size for i in range(desired_num_chunks + 1)]
    chunk_boundaries[-1] = file_size
    mini_chunk_size = 4096 

    for bi in range(1, len(chunk_boundaries) - 1):
        initial_position = chunk_boundaries[bi]
        file.seek(initial_position)
        while True:
            mini_chunk = file.read(mini_chunk_size)
            if mini_chunk == b"":
                chunk_boundaries[bi] = file_size
                break
            
            # 寻找换行或特殊的 Token 作为安全边界
            found_at = mini_chunk.find(split_special_token)
            if found_at != -1:
                chunk_boundaries[bi] = initial_position + found_at
                break
            initial_position += mini_chunk_size

    return sorted(set(chunk_boundaries))

模块三：状态初始化（从 Pair 到 Symbol 的架构升级）

一开始，我维护的是“字节对（Pair）”构成的列表，结果在更新时要疯狂处理左边界、右边界和重叠合并（如 e e e）的问题，代码极其臃肿且容易越界。

后来我重构了数据结构：直接维护每个单词当前的 词元（Symbol）列表，并将倒排索引改用 set，让增删查的时间复杂度直接降到 $O(1)$。

from collections import defaultdict
import regex as re

class BPETrainer:
    # ... 省略 __init__ 及 pre_tokenization 相关代码 ...

    def _inital_states(self):
        """
        构建基于“词元(Symbol)”状态的记忆列表与倒排索引
        """
        # 核心结构改动：存储每个词的频率与它当前的 Symbol 序列
        # 格式: [{"count": int, "symbols": List[bytes]}]
        self.word_states = [] 
        
        # 使用 set 替代 list，保证倒排索引的增删是 O(1) 操作
        self.pair_to_word_indices = defaultdict(set) 
        
        for word, count in self.words_counting.items():
            word_encoding = word.encode("utf-8")
            # 初始化时，每个 byte 就是一个独立的 symbol
            symbols = [word_encoding[i:i+1] for i in range(len(word_encoding))]
            
            word_idx = len(self.word_states)
            self.word_states.append({"count": count, "symbols": symbols})
            
            if len(symbols) < 2:
                continue
                
            # 统计初始 pairs
            for i in range(len(symbols) - 1):
                pair = (symbols[i], symbols[i+1])
                self.bytepair_counting_dict.add_count(pair, count)
                self.pair_to_word_indices[pair].add(word_idx)

模块四：基于差异（Delta）的高效状态更新

在核心的 merge 循环中，由于我们维护了 Symbol 序列，我们不再需要繁琐地去推导“左右邻居变成了什么”。我们采用“快照比对”策略：截取合并前的 Pairs 快照，生成新的 Symbol 序列后，再截取新的 Pairs 快照。两者做差集，即可得出哪些频次需要增加，哪些需要扣除。这彻底规避了连续字符重叠合并的 Bug。

    def merge_and_update_bytepair(self, most_frequent_pair: Tuple[bytes, bytes]):
        """基于 Symbol 序列的差异化更新逻辑"""
        new_token = most_frequent_pair[0] + most_frequent_pair[1]
        
        # 1. 获取所有包含该 pair 的单词索引 (套一层list防止迭代中修改set报错)
        word_indices = list(self.pair_to_word_indices.get(most_frequent_pair, set()))
        
        # 2. 全局状态更新
        self.vocab[len(self.vocab)] = new_token
        self.bytepair_counting_dict.push(most_frequent_pair, 0)
        if most_frequent_pair in self.pair_to_word_indices:
            del self.pair_to_word_indices[most_frequent_pair]

        # 3. 遍历并更新每个受影响的单词
        for word_idx in word_indices:
            state = self.word_states[word_idx]
            symbols = state["symbols"]
            count = state["count"]

            # --- 第一步：对当前状态建立“快照” ---
            old_pairs = [(symbols[i], symbols[i+1]) for i in range(len(symbols) - 1)]
            unique_old_pairs = set(old_pairs)

            # --- 第二步：生成新的 Symbol 序列 ---
            new_symbols = []
            i = 0
            while i < len(symbols):
                # 贪婪匹配目标 pair
                if i < len(symbols) - 1 and (symbols[i], symbols[i+1]) == most_frequent_pair:
                    new_symbols.append(new_token)
                    i += 2  # 成功合并，跳过两个旧的 symbol
                else:
                    new_symbols.append(symbols[i])
                    i += 1  # 未匹配，保留旧 symbol 并步进
            
            # --- 第三步：对新状态建立“快照” ---
            new_pairs = [(new_symbols[i], new_symbols[i+1]) for i in range(len(new_symbols) - 1)]
            unique_new_pairs = set(new_pairs)

            # --- 第四步：计算差异（Delta）并同步到全局计数与索引 ---
            for p in old_pairs:
                self.bytepair_counting_dict.add_count(p, -count)
            for p in new_pairs:
                self.bytepair_counting_dict.add_count(p, count)

            # 索引增删：利用 Set 的差集
            pairs_to_remove = unique_old_pairs - unique_new_pairs
            pairs_to_add = unique_new_pairs - unique_old_pairs
            
            for p in pairs_to_remove:
                if p in self.pair_to_word_indices:
                    self.pair_to_word_indices[p].discard(word_idx)
            
            for p in pairs_to_add:
                self.pair_to_word_indices[p].add(word_idx)

            # --- 第五步：保存更新 ---
            state["symbols"] = new_symbols

模块五：训练主循环

最后，将上述所有模块拼装在一起，我们得到了一个非常清爽的主循环。

    def train_bpe(self):
        """训练bpe流程"""
        # 第一步：预分词与初始统计
        self._init_words_counting()
        self._inital_states()
        
        # 第二步：迭代合并，直到满足词表大小
        iter_time = 0
        while len(self.vocab) < self.vocab_size:
            iter_time += 1
            # 找到最frequent的bytepair
            most_frequent_pair, max_count = self.bytepair_counting_dict.pop_most_frequent_valid()
            if not most_frequent_pair:
                break
                
            self.merges.append(most_frequent_pair)
            # 增量完成合并
            self.merge_and_update_bytepair(most_frequent_pair)

从数据中可以得出几个关键结论：

  • 绝对瓶颈：_init_words_counting 单函数独占 86.75 秒（80.4%），瓶颈在于正则分词和大文件的 I/O 读取。这几乎是不可绕过的"体力活"，后续可考虑用多进程并行切分来加速。
  • 堆操作开销可观：push 和 add_count 合计被调用约 80 万次，__lt__ 比较被调用 93.7 万次。说明 BPE 每轮合并后对倒排索引和堆的增量更新非常高频，valid_counts 字典的 get/set 也是隐藏的热点。
  • 合并循环本身很快：总共只执行了 743 次合并迭代（vocab_size=1000 减去初始 256 个字节 token），merge_and_update_bytepair 单次平均仅 0.097ms，说明基于 Symbol 快照的增量更新策略非常高效。
  • 总耗时约 108 秒：对于一个 5MB 语料、1000 词表的 BPE 训练来说，Python 单线程跑到这个量级已经是合理水平。如果要扩展到 GB 级语料和 5 万+ 词表，初始化阶段必须引入并行化。

总结

手写 BPE 的过程，实际上是一次对数据结构和计算机底层编码的重新审视。它不仅考验对算法理论的理解，更暴露了许多 Python 工程实践上的细节：从大文件的 I/O Chunking，到哈希表 $O(1)$ 复杂度的倒排索引设计，再到避免列表 $O(N)$ 删除操作的集合论应用。越是底层的基建代码，越需要打磨“优雅”。
